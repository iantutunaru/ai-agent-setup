# What to watch and how to note it

Without notes, a tester remembers what they expected or hoped to see (Fullerton ch. 9, "Taking Notes"; the
"happy face syndrome", "A Primer for Playtesting"). The notes sheet fixes in advance what gets written down, so
failures get recorded as readily as the good moments.

## The project's list

The watch-list (the entry's Playtests field) is the standing list: hypotheses from earlier tests and headless reads, each with the
levers to try if it shows. For a session, pick only the entries this build and setup can answer (an entry about one
weapon needs that weapon in play; a network entry needs two PCs) and route each as any question (references/human-or-batch.md).
An entry a playtest answers leaves the list: as a backlog candidate if it found a problem, deleted if not (the
list's own rule). An entry nobody can answer yet stays.

## The notes sheet

Three parts (Fullerton ch. 9, "Taking Notes", the playtest form):

1. **The questions**, each with its prediction and a box for what happened.
2. **During play:** tally marks and the match time for each category. Fixed categories beat free memory (Fullerton
   ch. 9, "A Primer for Playtesting", "Notice everything"):
   - confused: didn't know what was happening or what to do next;
   - surprised: something the user didn't expect, good or bad (Schell ch. 28, "The Second What": the most
     valuable result of a playtest);
   - frustrated: wanted to do something and couldn't;
   - idle or bored: waiting with nothing worth doing;
   - one category per picked question, e.g. "noticed an attack late".
3. **After each match:** the after-match questions below, plus the match facts: bot level, match settings, seat, result,
   length, replay file name.

Pair what was done (behavioural: time to notice, units lost) with how it felt (attitudinal: a rating and a why;
Wixon, in Fullerton ch. 9, "Metrics in Game Design"). A rating uses five labelled points, never 1 to 10 (Schell
ch. 28, "Surveys"; Fullerton ch. 9, "Data Gathering"). Keep the scale's statements the same across sessions so
builds can be compared.

## After-match questions

The assistant asks them in chat, in this order, before the user offers fixes. Shawn Patton's six, in Schell ch. 28
("Interviews"):

1. The most frustrating moment?
2. The favourite moment?
3. Anything you wanted to do and couldn't?
4. With a magic wand, what would you change?
5. What were you trying to do (your plan)?
6. How would you describe this match to a friend?

"Wanted" draws out small wishes and "wand" big ones; "doing" shows the player's goal; "describe" shows what they
think the game is about. Add one question per picked play question, asked as "were any parts...?" rather than
"would X be better?": players asked to design ask for it easier (Schell ch. 28, "Interviews"). Ask for the three
weakest moments rather than one. Twenty questions in a row exhaust anyone (Fullerton ch. 9, "Taking Notes"):
eight is plenty.

For a whole-match view, the user can sketch their tension over the match as a line, minute by minute
(Fullerton ch. 9, "Taking Notes", the dramatic questions). It shows where the climax fell, which sets beside
`design-lenses` pace reading.

## Cautions

- Watching the face more than the screen (Schell ch. 28, "How?") needs an observer. Alone, the user's marks
  and the replay stand in for one.
- Constant questions ruin a test (Schell ch. 28, "How?"). Questions come between matches, not during.
